# 产品设计简报

## 视觉基准

- 已调用 Product Design 的 `get-context`、`ideate` 和 `image-to-code` 流程。
- 用户选择了视觉方案 1。
- 基准图保存为 `docs/design/reference-dashboard.png`。
- 设计关键词：专业、克制、清晰、可信、高信息密度。

## 产品与使用者

产品名称：知乎问题总结工作台。

第一阶段主要使用者是内容运营人员。他们需要在一个 Windows 浏览器工作台中添加问题、安排处理、观察长任务、定位失败，并查看结构化分析和草稿结果。

## 核心任务

```text
添加知乎问题
→ 校验链接和内容
→ 保存到问题池
→ 加入处理队列
→ 查看 Worker 与实时进度
→ 查看观点提取结果
→ 打开最小草稿并进入人工审核
```

## 第一阶段用户目标

1. 在 30 秒内完成一个问题的手动添加和入队。
2. 不刷新页面也能看到任务阶段、进度和日志变化。
3. 一眼判断 Redis、Worker、模型和数据库是否可用。
4. 从问题或任务快速追溯到结构化分析与草稿。
5. 安全地处理重试、取消、忽略和删除。
6. 在没有 API Key 时仍能用 Mock 模式验证完整系统。

## 设计原则

- 桌面优先，适配 1440×900 和 1280×720。
- 主内容以表格、列表和清晰分组为主，不把每个区域做成卡片。
- 关键状态用文字、颜色和图标共同表达，不能只靠颜色。
- 操作日志靠近主工作区，帮助理解系统为何变化。
- 一个页面只突出一个主要操作。
- 表单使用明确标签、帮助文字和字段级错误。
- 高风险操作必须二次确认；默认自动发布关闭。
- 使用真实 API 状态，不用静态假数据冒充运行结果。

## 非目标

- 第一阶段不实现真实知乎回答采集。
- 第一阶段不实现完整观点聚类和文章生产。
- 第一阶段不实现 GPT 图片、信息图渲染或知乎发布。
- 不为了展示未来功能创建不可操作的复杂页面。

## 成功标准

- 用户可以从页面完成真实最小闭环。
- 正常、空、加载、错误、禁用和危险状态均可理解。
- 页面在两个验收视口无横向遮挡或不可达操作。
- 亮色和暗色模式均具有可读的状态对比度。
- 视觉实现通过与方案 1 的浏览器截图对比。

## 第二阶段扩展

第二阶段继续沿用方案 1，不改变主导航、颜色、字体、密度和桌面优先方向。

核心路径扩展为：

```text
查看采集回答
→ 理解共识、分歧和少数派观点
→ 追溯来源
→ 打开总结草稿
→ 同屏审核文章、图片 Prompt 和质量结果
```

用户确认手动图片 Prompt 工作流属于草稿审核过程。它固定放在草稿审核中间栏，支持复制中文/英文 Prompt、上传或替换手动生成图片、切换纯 CSS 模式和查看历史版本。

## 第三阶段扩展

第三阶段把“内容已经生成”推进到“可检查、可排期、可安全发布”，继续服务内容运营人员，不改变既有视觉方向。

核心路径：

```text
审核文章
→ 在草稿审核中编辑信息图并检查文字溢出
→ 生成 1080×1440 PNG
→ 固定文章和图片版本
→ 加入发布队列
→ 在日历排期并处理冲突
→ 发布前人工确认
→ 手动发布包或辅助发布
→ 查看执行记录和失败原因
```

第三阶段用户目标：

1. 不离开草稿审核即可完成信息图文案、背景、模板和版本审核。
2. 在下载前明确知道中文是否溢出、最终尺寸和使用的文章/图片版本。
3. 在一个发布中心同时看到内容准备、日历排期和执行记录。
4. 所有可能影响知乎页面的操作都先检查登录和验证码，并要求人工确认。
5. 在设置中理解当日 Token、费用、缓存、降级和预算暂停原因。
6. Prompt 修改永远产生新版本，不会无意覆盖生产版本。

信息图不是营销海报。它使用准确中文、明确来源和克制背景，信息层级优先于装饰；用户未上传背景图时，纯 CSS 模板仍然可以完成审核和 PNG 导出。
